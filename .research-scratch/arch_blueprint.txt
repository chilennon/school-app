1. Design Principles & Operating Reality
Every decision in this document follows from five facts about the environment this software will run in. Re-read these whenever a
technical choice feels ambiguous.
Reality Consequence for the build
The phone is the computer Low-end hardware Erratic, expensive data Varied digital literacy Paper still rules Most schools have no working desktop. The teacher's Android phone is the only device. Every
feature must be fully usable on a 360×640 screen with one thumb. Desktop is a bonus, not the
target.
Tecno, Infinix, itel, Samsung A-series. 2–4GB RAM, weak CPUs, limited storage. Hard ceiling on
JavaScript payload and runtime work.
Network is intermittent and metered. The app must be fully functional with zero connectivity and
must not silently burn data bundles.
Users range from confident to barely comfortable. No jargon, no hidden gestures, no multi-step flows
that can be abandoned halfway.
The report card that goes home is a printed sheet. Digital output that cannot become clean A4 paper
has failed.
The five design laws
1. Local first, always. The UI reads from and writes to the device. The network is a background concern the user never waits on. A
save must feel instant whether there are five bars or none.
2. One screen, one job. No dashboards crowded with widgets. Each screen answers a single question or completes a single task.
Depth over breadth.
3. The thumb owns the bottom third. Primary actions sit at the bottom of the screen where a thumb naturally rests. Nothing
important lives at the top.
4. Never lose a teacher's work. Autosave on every keystroke. No save buttons that can be missed. No session timeouts that discard
drafts. A teacher who loses an hour of score entry will never open the app again.
5. Speak the school's language. Use the vocabulary already on the walls and in the record books: term, session, CA, broadsheet,
position in class, form teacher. Never invent software words for things that already have names.
THE TEST FOR EVERY SCREEN
Hand the phone to a teacher who has never seen the app. If they cannot complete the task without being told what to tap, the
screen is wrong. Not the teacher.

2.1 Result Compilation & Report Cards
What it does
A subject teacher enters CA and exam scores for their class on their phone. The system computes totals, grades, subject positions, class
averages and overall position, then assembles a printable report card per student including behavioural ratings, attendance, and
teacher comments. At the end of the session it computes a cumulative average and a promotion decision.
How it works — the grading rules
Nigerian primary schools use a continuous-assessment split. The two common configurations must both be supported and set per
school:
Configuration CA weight Exam weight Notes
40 / 60 (most common) 40 marks 60 marks CA often broken into 2–4 tests plus assignments
30 / 70 30 marks 70 marks Used by some schools and most secondary schools
Store the split as school configuration, never hard-code it. Optionally allow the CA component itself to be broken down (CA1, CA2,
Assignment, Project) with the sum capped at the CA weight — build the simple single-CA-field version first.

2.2 Fee Management
What it does
Defines what each class owes per term, records payments as they come in (usually partial, usually by bank transfer), keeps a running
balance per student, issues receipts, and produces a debtors list per class on demand. It also gates result release on outstanding
balance.
THE SINGLE MOST IMPORTANT MODELLING DECISION IN THIS SYSTEM
Never store or update a balance. Payments are an append-only ledger. Balance is always computed as sum(charges) −
sum(payments). Inserts never conflict during sync, so a phone that was offline for a week cannot corrupt a student's account when it
reconnects. Every money bug you will otherwise spend weeks chasing disappears at this one decision.
Fee items to support
Item Behaviour
Tuition Compulsory, set per class per term
Bus / transport Optional, opt-in per student, sometimes varies by route
Feeding Optional, opt-in per student
Uniform / books One-off, usually first term or on admission
Exam fee Compulsory, per term
PTA levy Compulsory, per term or per session
Extra lesson Optional, opt-in
Development levy Compulsory, often per session
A student's charges for a term = all compulsory items for their class + the optional items they opted into. Sibling discounts and
scholarship waivers are common: support a per-student discount line as a negative charge rather than editing the fee structure.
Recording a payment
Almost no payment arrives through an API. Parents pay by bank transfer and send a screenshot on WhatsApp, or pay cash at the school.
So the primary flow is manual entry by the bursar or admin, and it must be fast:
Search student by name or admission number
Amount, date paid, method (cash / transfer / POS), bank reference or teller number
Optional note
Auto-generated sequential receipt number, unique per school per session
Receipt view that can be printed or screenshotted and sent back on WhatsApp
Online payment integration (Paystack or Flutterwave) is a phase-3 nicety, not a requirement. When you add it, treat the webhook as just
another writer into the same payments ledger.
The debtors list
This is the screen the proprietor will open most. Requirements: filter by class, sort by amount owed descending, show name, class,
amount due, amount paid, balance, and guardian phone as a tap-to-call link. Add a total at the top: "Outstanding this term: ₦1,240,000
across 87 students.

2.3 Student & Staff Registry
What it does
The single source of truth for who is in the school. Unglamorous, invisible to the proprietor, and the foundation everything else stands
on. Get the model wrong here and both features above become painful to fix later.
CORE MODELLING INSIGHT
A student is not in a class. A student has an enrolment that places them in a class for a given session. This separation is what
makes promotion, repeating a year, mid-session transfers, and multi-year history work at all. Scores and fees attach to the
enrolment, never to the student directly.
Student fields
Field Notes
Admission number Unique per school. Auto-suggest next in sequence, allow manual override for legacy numbers.
First / middle / last name Three fields, not one. Report cards and registers sort and display differently.
Gender Required — appears on report cards and registers.
Date of birth Often unknown or approximate. Make it optional; never block admission on it.
Guardian name Required.
Guardian phone Required. Second number optional. Normalise to +234 on save, accept 0803... on input.
Address Free text. Nigerian addresses do not fit structured fields.
Admission date Required.
Status active / withdrawn / graduated. Never delete a student — historical results depend on them.
Photo Deliberately excluded from v1. See §8.
Class structure
Nigerian primary schools typically run: Creche, Pre-Nursery, Nursery 1–3 (or Kindergarten), Primary 1–6 (sometimes labelled Basic 1–6),
each optionally split into arms (A, B, Gold, Silver, Diamond). Model class as { level
name, arm, level
order } where level

End-of-session promotion
One of the highest-value small features in the whole system. At session end the admin promotes a whole class in one action:
1. 2. 3. 4. Select the outgoing class and the new session
System computes each student's cumulative average and proposes Promote or Repeat
Admin reviews the list and flips any individual decision
Confirm → new enrolment rows are created in the destination class; Primary 6 students are marked graduated
Doing this by hand for 300 students is a day of work. Doing it in four taps is the kind of thing that makes a proprietor tell another
proprietor.
Staff records and assignment
Staff need: full name, phone, role, active flag. Two distinct assignments matter and must not be conflated:
Form teacher — owns a class. Writes the class teacher's comment, sees the whole class broadsheet, manages attendance.
Subject teacher — assigned to a (class, subject) pair. Can enter scores only for that pair.
One person is usually both. In a Nigerian primary school the form teacher often teaches most subjects to their own class, so make bulk
assignment easy: "Assign Mrs. Okoro to all subjects in Primary 3A" should be one action.

Three rules that make this safe
Rule 1 — client-generated UUIDs. Every row gets a uuid created on the device, not by the database. A replayed batch is then an
upsert on the same id rather than a duplicate insert. This single rule makes the whole pipeline idempotent.
Rule 2 — server timestamps for ordering. Device clocks on cheap Android phones drift, sometimes by hours. Send the device
timestamp for display, but let the server set server

Rule 3 — the outbox is never cleared optimistically. Remove an entry only after the server confirms that specific id. A failed batch
stays queued and retries.

4.4 Sync scope — protecting the data bundle
Never sync the whole school onto a phone. Scope by role:
Role Pulls
Teacher Current session + current term only. Only classes and subjects assigned to them. Students in those classes. No fee
data at all.
Form teacher The above plus full broadsheet for their own class.
Bursar Current term fee structures, all students (name, admission no, class only), payments. No scores.
Admin / head Current session, all classes. Historical sessions fetched on demand, not synced.
Add an explicit "Sync now" button next to the automatic behaviour. Teachers on metered data want to feel in control of when bytes
move, and a manual control buys enormous trust. Show approximate size: "Sync now (about 40 KB)"

6. Authentication & Security
6.1 Why email and password is the wrong choice
Many teachers have no email address they actually check. Typing a strong password on a cracked touchscreen is miserable and will be
done many times a day. Password reset by email fails when the email is abandoned. SMS OTP costs money per message and Nigerian
delivery is unreliable.
6.2 The flow that works
1. Admin creates the teacher — name and phone number. System generates a 6-character enrolment code (e.g. K7M2QX ).
2. 3. Admin shares the code — read aloud, written down, or sent on WhatsApp. No email, no SMS cost.
Teacher enters the code once on their phone. The device is enrolled and bound to that staff record. The Supabase session is
created and refreshed indefinitely in the background.
4. Teacher sets a 4-digit PIN. Thereafter the app opens with a numeric keypad. Two seconds to unlock.
5. Admin can revoke a device from the staff screen — ends the session and triggers a local wipe on next connection.
What the PIN actually protects
The PIN is a local device lock, not a server credential. It guards the copy of student data sitting in IndexedDB on a phone that may be
shared, borrowed or stolen. Store only a salted hash of the PIN locally, never the PIN. Lock the app after 15 minutes in the background.
After 5 wrong attempts, require the enrolment code again.
NON-NEGOTIABLE
On logout or device revocation, delete the entire IndexedDB database. Offline copies of children's names, ages, addresses and
guardian phone numbers must not persist on a device that is no longer authorised. Flush the outbox first if there is a connection;
warn clearly if there are unsynced changes.
6.3 Row Level Security
Multi-tenant leakage is the most damaging bug this system could have. Enforce isolation in the database, not in application code.

9. Printing Report Cards
The report card must become paper. Phones do not print. The honest, working flow:
1. App generates a clean HTML print view of the report card
2. Browser's Print → Save as PDF produces the file — built into Chrome on Android
3. Teacher or admin shares that PDF to a laptop or a business centre via WhatsApp for printing
This uses zero kilobytes of library code and produces better typography than any JavaScript PDF generator.

Closing note
The architecture in this document is sound, but it is not what will determine whether this succeeds. What will determine it is the number
of hours you spend sitting beside a real teacher at a real school, watching them use it and resisting the urge to explain.
Build the three features. Build them so they work with no network on a cheap phone. Print a report card that a head teacher would sign
without hesitating. Everything else can wait.
